SECS provider adoption: deferred work and qualification limits
============================================================
2026-10-29

Common design and active decisions in the nmr-provider-tools repository:
  notes/013_common_provider_lifecycle_design_20261028.txt
  notes/014_joint_provider_refactor_decisions_20261028.txt

These items do not waive the common design's correctness requirements or
constitute deployment approval. Independent work deadlines, original native
retirement, source retention, and removal of duplicate lifecycle/publication
owners remain implementation requirements, not caveats to defer.
Local qualification used ordinary published-SDK acquisition for both API and
CPU images. Disposable fixtures cover native retirement, selected-report drain
and the bounded scientific workflow below. Note 014 records the shared decisions
and exact proof scopes.

GPU and full-index qualification
-------------------------------

Owner: SECS scientific qualification maintainer. Revisit before claiming GPU
or full-index effects or deploying the corresponding scientific image.

The SDK 0.5.0 adoption replaced commit 19e356c's isolated SDK prefix with the
shared SDK's issued native-only installation lock. The API and scientific
images install the same published wheel; scientific dependency pins are unchanged.
Offline CPU qualification now includes the actual checkpoint, eight fixture
candidates and one GA generation, alongside input and scientific-boundary tests.
That establishes this bounded composition, not GPU behavior, full-index quality,
or numerical equivalence across the production workload. Run the maintained
GPU and published-challenge lanes before claiming those effects.

Scientific retry artifact identity
----------------------------------

Owner: SECS scientific binding and candidate-source maintainers. Revisit before
enabling a positive scientific retry count or claiming that a replacement child
uses the same loaded checkpoint and candidate index.

The worker-container snapshot in 5218429 holds worker TOML bytes for that
container lifetime; a restart captures the then-current operator file. The
checkpoint loader in 0ce5a64 hashes and decodes the same spec and weight bytes.
Neither establishes that a replacement child reads the same candidate index,
Parquet table, model cache or complete artifact bundle. Container read-only
mounts do not prevent the host from changing their contents.

The existing candidate manifest names the index and table and their expected
digests, but the runtime candidate loader reads paths and checks row counts; it
does not bind its loaded bytes to those digests. A small offline HNSWPQ probe
showed that FAISS can hash bytes as its loader consumes them and can detect
trailing data; a small Parquet byte-buffer probe also passed. The evidence is in
this session's offline tool receipts. Those probes do
not qualify the full index, resource usage, timing or concurrent host changes.
The local checkout has the manifest but not the approximately 23.7 GB index
or 1.0 GB table. On 2026-10-29 a low-priority, read-only scan on ProArt found
both files and their SHA-256 digests matched that manifest; its candidate and
checkpoint manifest digests also matched the local copies. The candidate
manifest digest is pinned by the published-challenge fixture, but the provider
does not use that fixture as runtime admission. This is a snapshot of bytes read
by the scan, not proof of what a worker subsequently loads or full-bundle
performance qualification.

Choose an upstream-owned verified-read or streaming seam for the candidate
index and table, and qualify the actual bundle, identity continuity, memory and
performance before enabling retries. Hashing candidate paths and reopening them
is insufficient; duplicating their loader in the provider would create another
scientific authority. Parquet readers may seek or read only part of a file, so
hashing only the chunks requested by the parser does not establish the full
manifest digest. Both complete artifacts must be bound to the same approved
manifest, whose identity is anchored independently of the mutable bundle, and
preserve the index-to-table row order; matching row counts alone
does not establish that correspondence. An offline two-row probe of the
`ScientificWorkerConfig` factory accepted a replacement Parquet file with
reversed rows and the same index and row count, with checkpoint loading stubbed.
It does not qualify
the model, replacement processes, full bundle or runtime resources.
The upstream loader's `allow_partial`
behavior also needs an explicit identity contract rather than an assumed full
file match. The local checkpoint loader still needs its first-child identity
bound across replacement children.
Retain the current single-search behavior until this proof and the other retry
eligibility, source, native-retirement and deadline requirements are complete.

Held Attempt capacity and availability
--------------------------------------

Owner: SECS runtime maintainer. Revisit before continuing unrelated Jobs while
an Attempt remains held.

The current provider has one scientific worker and one live bookkeeping slot.
These are different limits: a retired worker may leave a held claim even when
the scientific slot is free. Keeping only one claim and stopping on uncertainty
is simple, but the live-only owner is lost when the process exits. Retaining a
held claim while continuing other Jobs would need a bounded claim and byte budget,
confirmed worker retirement and fresh readiness, and local exclusion of the
held Job. Prove a held Job followed by an unrelated Job, capacity saturation,
stale discovery and shutdown before choosing that policy; do not add capacity
or a wait loop merely to imply persistence.

Only the original exchange's settled pre-write deadline refusal proves that no
request was dispatched. A caller's wait can expire while its shielded exchange
is still running, and remains unresolved. Do not infer no dispatch from a
generic timeout. An unresolved Attempt occupies the single live claim and stops
further Job processing; the process does not accumulate multiple live claims.

SECS asks the server for Jobs without a provider Attempt, using a fresh START
key for each selected Job. The server's feed excludes a Job after any Attempt
by that provider, regardless of its state; the feed is a read-only snapshot and
an unconfirmed START may still race. Restart does not reconstruct the old claim
or replay its START; the server owns Attempt expiry. Hello advertises capability
and refreshes the directory, not immediate free capacity or Job admission.
Withdrawing an offering does not itself gate the feed or admission for Jobs
selected for the provider, and any withdrawal acknowledgement can be unconfirmed.

Deployment and recovery rehearsal
--------------------------------

Owner: shared deployment maintainer and SECS deployment owner. Defer only the
deployment-specific rehearsal: no rollout is authorized or performed. Revisit
before deploying a selected installation.

The eventual deployment still needs its actual blocked-drain and native
containment procedures rehearsed under the common design. A finite Compose
stop grace is not proof that an unacknowledged report drains successfully.
An unconfirmed native owner keeps its sources and exclusion until settlement
is proved; status/socket disappearance or a replacement scratch root is not
that proof. Do not build provider-local recovery machinery just to avoid this
qualification. Any shared online barrier must establish its real continuity
preconditions; failed proof remains held for explicit operator resolution.
Disposable fixtures exercise pending-report drain and ordered stop. They do not
prove the original owner's cleanup or continuity on an installed deployment.
Rehearse those deployment-specific procedures before cutover.

Legacy obligations at cutover
----------------------------

Owner: SECS deployment operator. Deferred because this session does not perform
a deployment. Revisit before any legacy-to-shared-runtime cutover.

A future deployment cutover must inspect and settle the real legacy START,
active, terminal, and held obligations using their qualified owner before
switching runtimes. Local adapter tests cannot establish a deployment's empty
obligation set. Preserve existing keys, terminal bytes, shared delivery state,
and diagnostic history; do not delete them to obtain a clean migration check.
The implementation must retain the corresponding fail-closed admission guard.

Retry diagnostic detail
-----------------------

Owner: shared SDK diagnostics maintainer and SECS runtime owner. Revisit after
the release-critical availability/deadline adoption, when the shared bounded
renderer is qualified. Shared rendering work is tracked in SDK note 015 and
decision D125; SECS should integrate that owner rather than add a serializer.

Hello and discovery retry warnings currently show delay, HTTP status and request
identity but omit the original causal graph when no response exists. The generic
START/delivery callback also discards failure, wait and recovery detail. Controlled
backend-stage test failures establish this gap (D131); the richer rendering remains
deferred, not fixed. Preserve retry/stop/retirement rules and disclosure boundaries.

Direct session-retirement cancellation
--------------------------------------

Owner: SECS session maintainer. Revisit if a caller must cancel the retirement
coroutine itself and still attempt every independent cleanup port in that same
invocation. A raw cancellation can interrupt `SecsSession.retire` before later
ports are attempted. The shared SDK normally owns retirement in a retained
task, and a held owner can settle again; those facts do not prove that every
port runs during an independently cancelled invocation.

Fatal diagnostic interruption status
------------------------------------

Owner: SECS CLI and deployment maintainer. The reporting-failure guard preserves
an already-failed operation's exit status 1 and retains both original errors for
embedding callers. An actual SIGINT during fatal reporting therefore changes
raw termination status from -2 to 1; SIGTERM remains -15. This is not equivalent
signal preservation. The current Compose stop uses TERM; revisit only if a
selected supervisor needs the post-failure SIGINT distinction (D133).

Scientific diagnostic graph coherence
-------------------------------------

Owner: SECS scientific diagnostics maintainer. Revisit before operator tooling
relies on child-reported identities, references or counts as a validated graph.

The D148 operator projection bounds numeric facts and admits code-owned exception
names while omitting arbitrary child text. The original diagnostic object remains
unchanged. It does not validate graph coherence: an encoded synthetic frame with
exception_reference 999 and no corresponding node retains that numeric reference.
These displayed values establish no retry, retirement or API-effect permission.
Reference and count consistency checks remain deferred, not qualified by the
privacy, original-task retention or physical-cleanup tests.
