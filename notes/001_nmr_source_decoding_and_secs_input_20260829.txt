Bruker experiment decoding and SECS input design
================================================

Date: 2026-08-29
Status: candidate design; implementation is not authorized


Purpose
-------

Define the smallest Python boundary that can turn one original Bruker 1D proton
experiment into the 10,000-point spectrum consumed by SECS.

The first admitted source is one Bruker experiment directory such as
``F3697/1``.  Other vendor formats, generic spectrum files, and a Bruker study
containing several numbered experiments are unsupported for now.  They should
produce one unrecognized-input outcome rather than speculative parsing or a
hierarchy of format-specific validation errors.

The molecular formula is a separate elucidation input.  It is not part of the
vendor dataset and does not pass through spectrum preprocessing.


Decision
--------

Keep source understanding separate from the SECS input profile:

    API/provider-materialized Bruker experiment directory
                            |
                            v
                  read_bruker_experiment
                            |
                            v
                  neutral 1D proton spectrum
                            |
                            v
                   encode_secs_spectrum
                            |
                            v
           float32[10000], ascending -2..10 ppm

``nmr_preprocessing`` owns Bruker decoding.  It imports neither SECS nor Torch.

``secs_input`` owns the SECS grid: ppm range, interpolation, scaling, length,
and final Float32 cast.  The existing ``secs_inference`` package checks that
profile against checkpoint configuration and continues to own model-order
reversal, device, and compute dtype.

Use nmrglue behind the Bruker boundary.  Do not expose nmrglue dictionaries as
our contract.  Its vendor dictionary is Bruker-specific, while its universal
dictionary deliberately omits source information and may represent unavailable
fields with generic defaults.  Copy only the verified values consumed by the
neutral processing path.


Admitted input
--------------

The reader accepts one already materialized, read-only Bruker experiment
directory.  Relevant members of
``/home/ra/Downloads/500 HD NMR/F3697/1`` include:

    F3697/1/
    |-- acqus
    |-- fid
    |-- pulseprogram
    `-- pdata/1/
        |-- 1r
        |-- 1i
        |-- procs
        `-- ...

The whole experiment directory is supplied.  A client should not extract and
upload only ``fid`` or ``1r`` because the accompanying acquisition or processing
parameters are required to interpret those numeric bytes.

The first slice recognizes an experiment only when it can obtain:

* acquisition parameters from ``acqus``;
* ``pdata/1/1r`` together with its ``pdata/1/procs`` parameters;
* verified one-dimensional ``1H`` identity and the facts needed to construct a
  ppm axis.

This is recognition, not a general validator for every legal TopSpin dataset.
Files that do not establish the supported case are simply unsupported.

The first slice recognizes only ``pdata/1/1r`` as input.  It does not search
other ``pdata`` directories, choose among them, or process ``fid``.


Example: F3697/1
----------------

The inspected dataset is an 89 MB Bruker study named ``F3697`` with 18 numbered
experiments.  Uploading the whole study would be ambiguous and is not part of
the first slice.

``F3697/1`` alone is one 500 MHz, CDCl3, 1D ``1H`` experiment.  It contains both
a raw ``fid`` and a processed ``pdata/1/1r`` representation.  The frontend's
pinned NMRium loader decodes both and its preference hierarchy selects the
processed representation.  The first Python slice reads that processed pair
directly.  Raw-FID processing is deferred until a separate slice has a real
raw-only fixture and its own scientific qualification.


Upload boundary
---------------

The browser may let a user select the ``F3697/1`` folder directly.  The API,
however, needs one immutable artifact.  Its future input schema must provide one
bounded byte sequence that preserves every admitted member's bytes and relative
path.  A ZIP is one non-normative illustration:

    F3697-1.zip
    |-- acqus
    |-- fid
    `-- pdata/1/...

The envelope is not a Bruker source format.  The API owns its schema and
admission.  The provider adapter safely materializes the schema-defined payload
root and mounts it unchanged at the preprocessing container's fixed read-only
input path; it does not inspect Bruker files to discover that root.  Only
``read_bruker_experiment`` decides whether the mounted tree is supported.  The
formula travels directly to the elucidation workflow, separately from this
artifact.

The current NMR API does not yet implement artifact-backed Job inputs.  This is
a consumer requirement for that future contract, not a claim about an existing
upload route.


Neutral values
--------------

The neutral seam needs only two values:

``ReaderReceipt``
    The selected source-relative files, Bruker reader identity and version, and
    the verified source facts used to decode them.

``Spectrum1D``
    Float64 ppm coordinates, real intensities, and ``ReaderReceipt``.

The Bruker reader constructs these values only when the fields needed to decode
the processed representation are present.  The SECS encoder owns its numeric
input preconditions.  Do not add optional metadata without a current consumer
or substitute placeholder facts for absent ones.

Do not add ``NmrDataset``, a reader registry, a generic metadata model, or a
processing-event framework for this slice.  There is one admitted experiment
and one explicit reader.


Bruker decoding
---------------

``read_bruker_experiment(root)``:

1. Opens only the fixed admitted paths relative to ``root``; archive path and
   link admission remain the materializer's responsibility.
2. Uses nmrglue to decode Bruker parameters and numeric arrays.
3. Translates only the acquisition and axis facts consumed downstream.
4. Decodes ``pdata/1/1r`` with ``pdata/1/procs`` as ``Spectrum1D``.

The raw ``fid`` may remain in the uploaded original directory, but this slice
does not read or process it.


SECS encoding
-------------

``encode_secs_spectrum(spectrum)`` alone owns:

* ascending ppm sorting;
* interpolation over the inclusive -2 through 10 ppm interval;
* exactly 10,000 equally spaced points;
* linear minimum/maximum scaling to 0..1;
* one final Float64-to-Float32 cast.

The encoder accepts paired, finite Float64 arrays with at least two distinct ppm
coordinates and the coverage required by the fixed grid.  The first slice
characterizes JavaScript ``xyEquallySpaced`` and ``xRescale`` behavior only for
the admitted processed Bruker fixture.  This is not a reason to create a generic
interpolation abstraction or an edge-case matrix for unsupported inputs.

The output remains in ascending ppm order.  ``SecsInference`` retains its
checkpoint-owned max normalization and reversal into model training order.


Container boundary
------------------

Bruker parsing and SECS encoding run in a dedicated preprocessing image, not on
the host and not in the checkpoint-bearing inference process.  The image
composes ``nmr_preprocessing`` with the Torch-free ``secs_input`` closure; it
does not install ``secs_inference`` or checkpoint dependencies.  The lane has:

* no network;
* a read-only root filesystem and input mount;
* a fixed non-root UID/GID, dropped capabilities, and no-new-privileges;
* bounded memory, PIDs, CPU, wall time, and scratch tmpfs;
* one explicit writable output mount;
* no engine socket, credentials, checkpoint, source checkout, or unrelated host
  filesystem access.

It emits ``spectrum.npy`` as Float32 with pickle disabled and a bounded
``receipt.json``.  The receipt contains ``ReaderReceipt`` and the SECS encoding
profile.  It contains no vendor-file copy, artifact identity, or access
capability.  The provider adapter binds this scientific receipt to the API-owned
artifact digest.

Container isolation limits authority and parser effects; it is not described as
a hostile-code sandbox.


Outcomes
--------

The first slice needs one domain outcome:

``UnrecognizedSpectrumInput``
    The materialized directory cannot produce the single supported processed
    Bruker 1D proton spectrum.  The underlying recognition or decode cause is
    preserved for operators.

This name describes a boundary outcome, not a required exception hierarchy.
Encoding, container, and runtime faults remain preprocessing or execution
failures.  The API adapter owns concise user-facing wording and preserves the
underlying cause and bounded receipt evidence.


Qualification
-------------

The implementation is admitted against the existing processed ``F3697/1``
representation plus a small synthetic encoder fixture.

The Bruker proof establishes:

* the decoded nucleus, observation frequency, spectral width, and ppm axis;
* decoding of ``pdata/1/1r`` with ``pdata/1/procs``;
* rejection of a tree that does not establish that supported pair.

The SECS proof establishes exact grid endpoints, length, order, scaling, and
Float32 conversion against a reference vector recorded from frontend revision
``5ab78f61e9fb679f3f0b9823be5217ae250e213f``.  The local fixture records that
revision and the characterized frontend encoding profile.

No test claims support for a format or Bruker structure outside these fixtures.


Implementation order
--------------------

1. Record the pinned frontend's processed ``F3697/1`` SECS vector, exact
   revision, and encoding profile used to produce it.
2. Add the two neutral values and ``encode_secs_spectrum``.
3. Admit one reviewed nmrglue release through the existing lock and wheelhouse
   lane, then add ``read_bruker_experiment`` for the processed representation.
4. Add the preprocessing container lane and prove the processed path.
5. Add the API adapter only after the NMR API releases an artifact-backed Job
   input contract.

Any later source format is a separate design and dependency decision.  That
design must prove whether the existing neutral seam is sufficient rather than
assuming it is permanent.


Rejected scope
--------------

The first slice deliberately excludes:

* whole Bruker studies containing multiple experiments;
* processed representations outside ``pdata/1``;
* raw Bruker FID processing;
* multidimensional Bruker experiments;
* Varian/Agilent, JCAMP-DX, JEOL JDF, NMRium, and generic numeric arrays;
* a plugin registry or client-supplied format name;
* arbitrary URLs or reader-side archive extraction;
* automatic choice among ambiguous experiments or representations.

These inputs are unsupported in the first slice, not rejected permanently.  We
do not add speculative parsers, fallbacks, or format-completeness validation
before a later format is deliberately admitted.
