SECS adoption of the shared API proxy and outbox
================================================

The joint design is nmr-provider-tools notes/020_shared_api_proxy_redesign_20261030.txt
and 021_container_network_topology.txt. The shared-package owner owns the proxy,
outbox and SDK; SECS owns its integration and scientific lifecycle.

First deployment
----------------

Run all four providers and the shared outbox against the existing nmr.localhost
API through one independently managed API CONNECT proxy. All providers use one
shared outbox intake. Retire eight replaced API proxies and unused private API
and delivery socket resources through their owners. Source and build results do
not prove live operation; remote hosts require their own observed deployments.

Provider and outbox changes leave the proxy running with its socket volume intact.
Its first deployment supports live capacity, logging and allowed CONNECT authority
controls. The outbox independently reloads capacity, retry and logging settings
from the same operator-owned file. Process identity, network setup and socket
storage remain host deployment responsibilities. Providers do not register with
or edit this operator file. The API origin, signing identity, TLS and scientific
source/store/interpreter access remain with their existing client owners.

Configuration replacement and service interruptions during cutover are accepted,
including while delivery has pending work. Do not add staging, rollback or
incumbent-continuity machinery as a prerequisite. Existing queue ownership,
accepted-command bytes, signing/TLS and effect-uncertainty rules continue to apply;
never overlap queue owners, discard acknowledged work or replay an ambiguous START.

Current SECS seams
------------------

deployment/provider_deployment.py::_apply_delivery_binding currently reads the
provider's selected static binding, obtains its private delivery intake grant and
mounts definition and input files. _apply_api_route merges api/api-init roles and
sets SECS_API_PROXY_SOCKET. src/secs_inference/provider/config.py requires a
binding definition and name; main.py loads that binding, builds API settings and
constructs DeliveryClient from its endpoint and delivery retry settings. These
are current implementation facts, not the new shared contract.

The provider signs its own API requests. Its scientific session constructs the
terminal result, and the existing SDK lifecycle hands it to delivery. The worker
uses network_mode: none; interpreter and upload-store connectivity belong to
separate provider network policy. _admit_runtime_volumes protects lifetime,
sources and session storage. Preserve these boundaries and their owned grants.

The deployment inventory includes api/api-init and stop retains containers.
Removing those roles from the new strict inventory alone would make old project
containers foreign, blocking status and cleanup. Current normal deployment
commands do not retire their private route volume.

SECS changes
------------

* Adopt the issued shared SDK grant interface for both host-owned socket volumes.
  Add read-only nocopy mounts and supplementary API/outbox access groups to the
  provider without replacing existing mounts, groups or worker dependencies.
  Declare the shared volumes external and never initialize, relabel or delete
  them. A missing volume fails client launch. No provider-owned API proxy,
  initializer, cross-project dependency or direct-network fallback remains.
* Replace the static binding selection in config.py, provider.toml.example,
  deployment/provider_deployment.py and main.py with the shared SDK's actual
  client configuration and handoff. Keep SECS's own issued credential, API origin,
  trust and relevant API timeout/topology settings with the provider; remove copied
  host router policy and the static registration/per-provider intake assumption.
  Do not invent SDK symbols, wire fields, socket paths or an unissued release.
* Use the SDK to hand off the exact terminal operation/body and Job/Attempt and
  API/provider identity, along with usable issued credential, optional CA and
  publication settings. An in-memory key/context or provider-container path is
  not sufficient publication material. The SDK/outbox own the format and fresh
  publication signing; SECS does not serialize private keys into logs or add a
  second protocol. Accepted result and publication material must be durably
  committed together before acknowledgement. An uncertain acknowledgement keeps
  the producer obligation and follows the existing identical-handoff rules.
* Preserve API signing/TLS and existing START, native retirement, scientific
  input retention and result semantics. A durable outbox acknowledgement proves
  acceptance for delivery, not API acceptance. Outbox removal or provider exit
  cannot remove accepted work. Credential revocation or missing old publication
  inputs must leave the affected work held and visible through the outbox owner.
* Adapt the maintained deployment retirement path to admit and stop the observed
  old six-role graph from the upgraded main checkout, including status and retry
  after interruption. Inspect owner and mounts, stop using existing ordering,
  remove only the old admitted API roles and their unused private volume. Preserve
  ownership evidence on failure. Do not remove lifetime, sources, session, shared
  API/outbox storage or another owner's delivery resources. The shared owner
  retires old delivery intakes and delivery-owned API routes after their users stop.
* Adopt the actual issued SDK through existing lock, wheelhouse and image build
  paths. Adjust installed-version checks and focused tests with the changed input
  contract. Do not copy SDK source or build a second configuration model.

The shared outbox socket is a submission-only capability. It accepts a result
handoff and returns its durable acknowledgement or refusal; it exposes no pending,
status, inventory or capacity reads. Operator inspection remains separate.
The shared owner validates the submitted credential's structure and matching key
pair, keeps publication material out of replies, and retains bounded per-provider
and total backpressure. Local parsing alone does not prove API issuance or
authorization; the API authenticates publication. The shared socket trusts its
local submitters and does not cryptographically authenticate each provider. A
conflict refusal for a guessed matching identity can reveal limited existence
information, even though there is no queue-read operation.
This limited disclosure is accepted for the controlled host.
Private durable publication material, database/WAL and backups stay with its
owner and out of status, diagnostics and public artifacts. SECS does not own
outbox queue policy or independently alter its stored rows.

SECS currently configures a 2 MiB pending terminal-body budget in main.py. The
shared intake must accept that supported body plus separately bounded credential,
CA and encoding overhead; retain the body budget's meaning without shrinking it
or truncating results. Account for retained publication material's storage
footprint in the outbox's capacity limits.

SECS admission and retained results
-----------------------------------

runtime.py discovers at most one Job with has_provider_execution_attempt=False,
waits for the controller and drains it before proceeding. main.py configures one
live Attempt and a 2 MiB pending terminal-body limit. SECS does not directly call
delivery pending/status for admission. A full or unavailable outbox can therefore
be discovered only when submitting the selected result: retain that exact handoff
under the existing live claim, retry using SDK backpressure rules, and do not admit
another Attempt while it remains unacknowledged. Preserve the bounded claim and
stop/drain behavior rather than adding a capacity read or registration. After
durable acknowledgement the outbox owns the accepted work and its bounded queue.

The API's unattempted-Job feed and existing START uncertainty rules remain the
authority for discovery, including after restart; do not infer queue membership
from that feed or promise the old pre-start outbox capacity check. An unaccepted
result's live owner is not durable across provider process loss: the existing
pre-ack producer-crash uncertainty remains. A lost acknowledgement must settle
the original exchange and retry the identical handoff through a submission-only
SDK; do not require a status lookup. Verify idempotent replay and refusal behavior
with the issued SDK before claiming this works, including full/unavailable outbox,
lost acknowledgement, provider stop and restart. A full refusal after science is
backpressure, not evidence that capacity was reserved before science started.
An acknowledgement must describe the inputs actually retained: different
publication inputs cannot silently replace the original or be reported as stored.
Verify the provider-relative Attempt-filtered feed against the deployed API during
integration, retaining the original provider identity.

Local cutover and proof
-----------------------

1. Coordinate the SDK's concrete grants and handoff with the shared owner, then
   build through maintained targets in the main checkout. Start the proxy and
   outbox through their independent owner, then bring up ready providers using
   their maintained workflows. No separate provider registration is needed.
2. Run make test/deployment and affected existing provider/delivery tests. Adapt
   tests/deployment_e2e/test_api_route.py to a test-owned route and the shared
   grant; disposable authored-API fixtures remain independent. Check that both
   socket mounts/groups coexist with scientific grants, absent external volumes
   fail, and normal cleanup leaves shared storage intact. Use a one-off docker
   run only after checking that the exact borrowed volume exists: nocopy alone
   does not prevent implicit creation.
3. Stop and retire the old SECS graph through the maintained owning path, then
   apply the new configuration and start with provider/deployment/up. Service
   interruption and replacement of old configuration are acceptable; do not
   block on an empty queue or individual retry receipts. Preserve actual storage
   and obligations using their existing owners, without manufacturing settlement.
4. Observe the actual provider and worker, selected images, shared grants, signed
   API/startup evidence and outbox intake. Check logs, health and restarts; with
   available work observe outbox progress and account for pending/held items. A
   paused publisher with wrong material is a blocker, not an ordinary retry.
   Verify that provider replacement leaves the proxy and outbox running. Joint
   completion additionally needs all other providers and retirement of all old
   proxy and private intake roles; count roles, not only total containers.
5. Each remote host separately acquires issued source and artifacts via GitHub,
   builds locally and uses its maintained deployment workflows. No bundle
   transfers, private overlays, side checkouts or one-off operational repairs.

Alternatives and follow-up
--------------------------

An outbox alone cannot serve direct provider API exchanges. Combining it with the
proxy would couple proxy availability to outbox replacement and queue recovery.
Separate services and socket grants preserve the required independent lifecycles.
Keeping a static provider registry or separate intake sockets would require an
operator update for each joining provider; a self-contained SDK handoff supplies
publication inputs with each result instead. Moving signing into the proxy would
expose provider keys to a transport that does not need them.

Tier 2: client help/status and safe API/store failure context, small regressions
for observed integration faults, and an optional standalone signed API check if
an operator need remains. Owner: SECS deployment/runtime maintainers; trigger:
joint deployment works or a demonstrated blocker cannot be resolved by existing
checks. One-off checks must enforce exact external-volume existence. These changes
must not restart or replace the proxy.

Tier 3 excludes registry/registration systems, general migration frameworks,
per-provider proxy fairness and speculative load or chaos campaigns. A demonstrated
integration failure belongs in Tier 1 regardless of category. SDK socket names,
client symbols and handoff representation are shared-owner decisions to settle
before release; they are not inferred from the superseded static-binding design.
